# 0004 — Identity and credential authority

Status: accepted design, amended 29 October 2026 (the owner's password from the platform page), 31 October 2026 (personal hosts), 2 November 2026 (credential-custody limits) 3 November 2026 (the platform pages decide per person), 3 November 2026 (team members behind Access), 4 November 2026 (removing a team member) and 5 November 2026 (support access for owners and administrators); its connected-accounts custody row and default-approval sentence superseded by [ADR 0008](0008-connected-accounts-omnigent-mcp-registry.md). Fork mechanisms, the platform key service, GitHub wiring and private computer route exist in source. The owner's installation has exercised the assembled path on Cloudflare; the staging release gates and complete security qualification remain open.

## Context

Generation fencing prevents an old computer from reclaiming current authority. Credential encryption protects stored records but does not prevent authorized plaintext use. Runners need broad application access, so their tokens cannot be described as isolated computer-only credentials.

## Decision

Omnigent owns each stable host ID. A container start has a separate platform generation and a granted start attempt. The host receives its identity and fresh launch token directly; restoring files must not create another host identity. The token remains in supervisor/host memory and process environments, never a login file or checkpoint. Code on that computer can read the token; this is within the supported trust model.

Managed-host registration requires that host's launch token. Owner bearer fallback must not claim a pending/managed host, and a superseded token must not displace the current incarnation. Interception binds the trusted computer/generation to that host. These rules prevent cross-computer registration; they do not prevent broad owner-equivalent application access through runners.

Runner tokens are short-lived owner bearers marked `delegated`. The fork refuses them for approval answers through either route, policy updates/deletes, default-policy creation, replacing a session's agent, and account/credential administration under `/auth/*` and `/oauth/*`. The private computer route additionally blocks sharing mutations and protected administrative/approval paths. The runner may consume a human-approved MCP call only against the server's recorded verdict, bound to the exact call/arguments, session or actor and connection generation, and consumed once. Caller-supplied acceptance is insufficient.

Delegated runners may still add session policies, cap sub-agent costs and manage user agents. (Superseded by [ADR 0008](0008-connected-accounts-omnigent-mcp-registry.md): connected accounts are Omnigent's MCP registry under Omnigent's own policies as they are, with no generated default approval policy.) Added policies can affect state read by other policies, leaving a known approval-bypass risk. These narrow restrictions do not promise confinement of hostile code: runners can reach the person's other conversations and computers' work. A fully scoped runner principal remains later work. The `harness_install` feature stays disabled in the platform image.

**The platform's one account-administration power (amended 29 October 2026).** The platform can set the password of exactly one account: the installation's named owner (`OMNIGENT_ACCOUNTS_INIT_ADMIN_USERNAME`). Only the owner reaches the page that does it: it sits behind Cloudflare Access and the owner pin, with the same origin, fetch-metadata and request-intent checks as the other platform pages. The web Worker hands the password to OmnigentServer, which alone calls the server's `/_cfo/owner-password` with a signed, timestamped, single-use request. The key is derived from the cookie secret, whose holders can already mint the owner's sessions. OmnigentServer never forwards a `/_cfo/` path from a browser or a computer, so neither a runner nor anything on a computer can use this power. Setting the password signs the owner out of every Omnigent session, and the page reports success only once the change is durable. The installer no longer chooses a password anyone knows: the owner chooses it on this page the first time, and the same page is the owner's reset.

**The platform pages decide per person (amended 3 November 2026).** Ingress authenticates; it does not decide what a person may do with a computer. The pages turn the admitted identity into a person through one seam, which answers "the installation's owner" while the owner pin admits nobody else and becomes membership-aware with teams (WP8.3). The computer's WorkspaceDO decides from that person and the computer's owner binding (ADR 0001): its owner may do everything the pages offer; anyone else is answered as if the computer did not exist; a human administrator may see it in the fleet, stop it, remove it while it is awake and Omnigent no longer calls it and, while its removal is pending, sign its logins out and finish the removal (amended 4 November 2026, below), and, since 5 November 2026, open its page, its status and its terminal and change its size to help its owner (support access, below). Signing in on it is the owner's alone, and an administrator's runner gets nothing: a cloud computer's runner has no Access identity and its private route never reaches the pages. Request-intent tokens and terminal capabilities are bound to the person as well as the Access session. **Limit:** a personal host reaches the installation through the Cloudflare One Client signed in as its person, so code on an administrator's laptop reaches the pages as that administrator; separating a device's sign-in from a browser's belongs to WP8.3 and WP8.5.

**Support access for owners and administrators (amended 5 November 2026, owner decision D62).** Every team owner and administrator, and the installation's owner, may manage everyone else's cloud computers, to help people who are not technical. They act *on* the person's computer, never *as* the person: the owner binding never moves (ADR 0001), and Omnigent still names the computer's own owner on every launcher call.

- *What an administrator may do on someone else's computer.* Open its page and its status, wake it through Omnigent's own start (the fork allows an administrator's, from a browser sign-in), drive its terminal, change its size and stop it, as well as the fleet and removal actions above. WorkspaceDO's page front decides it from the same three levels (`owner`, `admin`, `none`); `admin` is widened rather than a new level added, since every owner and administrator gets it. A member still finds anyone else's computer not found.
- *Sign-ins stay the person's own.* An administrator never starts, continues or cancels a Claude or Codex sign-in, never reads an attempt, its link or its code, never signs the computer out outside a removal, and never records a revocation or changes a staging switch. Their page shows each service's sign-in state (signed in or not) and says that the person signs in themselves; their page state carries no attempt at all. The same rule holds in the fork for MCP and GitHub logins and harness credentials: an administrator sees a member's connection state and may disconnect one, but never connects one for them.
- *The terminal.* An administrator's terminal capability is bound to their own Access subject and session, as an owner's is, and an upgrade from anyone else is not found before the capability is looked at. A computer has one terminal window, so an administrator opening it closes a window its owner has open. The terminal reaches what the person's computer holds, their saved logins included. That was already reachable through any of the person's threads (owner decision D52); D62 makes it plain rather than new, and the manual tells members.
- *Records.* Each support action logs `page_support_action` with the computer, the action and the acting person's member ID (`member:<id>`, or `installation` for the installation's owner), never an account or an address. WorkspaceDO's operation journal records the actor beside each page action's outcome, inside the outcome it already keeps, so its storage format is unchanged. A list for the member of what administrators did on their computer is later work.
- *Unchanged.* Runners and hosts gain nothing: a cloud computer's runner has no Access identity, and the fork grants support access to interactive browser sign-ins only. The personal-host limit above applies as before: code on an administrator's laptop reaches the pages as that administrator, now with the terminal and size too.

**Personal hosts (amended 31 October 2026).** The owner may connect their own machines as ordinary Omnigent hosts of the installation (owner decision D48), through the Cloudflare One Client signed in as the owner (D47): Access admits such a device for the installation's application only, device enrollment admits only the owner, and the web Worker's checks are unchanged. Such a host registers with the owner's Omnigent sign-in, not a launch token, as any laptop host does, so it holds a long-lived Omnigent login and refresh grant and runs agents with the owner's local account. This is an accepted exception to the custody rules below, which govern cloud computers: a personal machine is the owner's, and its compromise is a compromise of the owner's account. Revocation is the device's Zero Trust registration plus the owner's password change, which rotates the account generation ([personal hosts](../operations/personal-hosts.md#a-lost-or-stolen-machine)).

**Team members behind Access (amended 3 November 2026, owner decision D50).** An installation can admit its team's members, each tied to their own Omnigent account; until the team model reaches the installation's Omnigent pin, and team admission is turned on, ingress admits only the owner as before.

- *Who reaches the site.* Access decides, through one Access group the installer creates for the installation's members (the owner's address at first). With `TEAM_ADMISSION=members`, ingress admits whoever Access admitted for this application and no longer pins the owner; it still checks the assertion, the hostname and the origin. Omnigent decides who they are.
- *Who they are.* The web Worker passes the Access identity it validated (issuer, subject, audience, address, whether it is the owner) to OmnigentServer in an internal header no client can set (every `x-cfo-` header a client sends is stripped on both paths). OmnigentServer turns it into Omnigent's signed identity envelope (`x-omnigent-external-identity`, an HMAC under a key derived from the cookie secret by a domain-separated HMAC, lasting at most 60 seconds, which Omnigent enforces with 10 seconds of clock skew) and strips any envelope a client sent. Omnigent binds `(issuer, subject)` to one team member, never by address, and refuses an Omnigent credential that belongs to anyone else: a valid sign-in for Alice with Bob's cookie, bearer, refresh grant, magic link, device code, runner binding or launch token, OAuth callback or WebSocket handshake fails, credentials that name their account only once resolved included. The installation's founding owner binds once, on first entry from a browser (the pin and the owner's own browser sign-in; never a CLI's, a host's or a grant's credential), and only while that membership has no binding; everyone else, a second owner included, through a single-use invitation for their address, or a link invitation proved with the account's password. With `required`, a person's credential is honoured only through Access, so a computer's route carries runner and host tokens only.
- *Changing who is admitted.* Omnigent's team page (owners and admins, from a browser sign-in only) invites, changes roles and suspends; each change commits a higher admission revision, and the server image's adapter sends the whole list to `platform.internal/access/v1/admission`, signed with the launcher's key under its own protocol line. The platform Worker writes it into the member group, and only that group's include list, with an account token whose permission ("Access: Organizations, Identity Providers, and Groups Write") Cloudflare cannot narrow to one group; see [secret custody](../secrets.md). A list naming none of the team's current active owners, a widened group and a lower revision are refused; the list comes again at an unchanged revision (at an invitation's expiry and hourly), and the platform compares it with the group and repairs drift, recording a revision only once Access holds the list. Suspension rotates the member's registration and retires their launch tokens and runner bindings, so every token from before it stays dead and reinstatement needs new ones; Omnigent's own checks never depend on Access's list.
- *The platform pages* decide each person through the membership seam (`pages/member-seam.ts`) in `members` admission, asking the server which member an Access identity is bound to on every page request: an active member reaches her own computers and an owner or admin the fleet view, as WorkspaceDO decides per computer; only the installation's owner, the active owner whose account the platform recognises as the installation's named owner, keeps the owner's own pages. A matching address is not enough, and an unbound, suspended or removed identity gets no page. Only `owner` admission, a team of one, answers the pinned owner without asking the server.
- *Known limit: device sign-ins.* A laptop signed in to the Cloudflare One Client as a person reaches the installation as that person, so code on it reaches the platform pages with that person's powers (an admin's laptop, the admin's). For a team of one this is the accepted rogue-agent risk on the owner's own machine; telling a device's sign-in apart from a browser's (for example a path application for `/platform/` without client sign-in) is WP8.5's. Omnigent's own administration already needs a browser sign-in.
- *Unverified:* the member group's reconciliation against the live Access API, the assertion's claims under the One Client, and whether `sub` is the same for a person's browser and device sign-ins (a different `sub` is refused, never merged) are to be checked on staging.

**Removing a team member (amended 4 November 2026, WP8.9).** An owner or admin removes a member from Omnigent's team page (an admin removes members only; nobody removes themselves, the team's last active owner or the installation's named owner). One Omnigent transaction deletes the account, revokes every credential and grant it holds (browser, CLI and device sign-ins, runner and launch tokens, shares, schedules, approval authority) and the pending invitations they could still use, retires the membership with its identity bindings and records the removal. Then, as a suspension does, open streams end at once and the member group is sent without their address, which the reconciler reads back before it reports success. Their cloud computers get Omnigent's own `terminate`, as when a person deletes one: each stops after saving and keeps its saved logins until its removal is finished. The team page shows these steps and retries the unfinished ones.

- *The admin's Remove of a computer stays gated.* Recording a removal from the pages is offered and accepted only for a lost host (FH-31): a computer that is awake while Omnigent has not called it for an hour, with no removal recorded. "No contact" counts only while the computer is awake: Omnigent calls an asleep or stopped computer only to wake it, so an asleep computer, a member's usual state, is never "not connected", and neither its owner nor an administrator is offered its removal; its owner deletes it in Omnigent (Settings, Computers), whose `terminate` records the removal. One pure rule (`removeOffered`) decides it for the confirmation page, the cards and WorkspaceDO, and a POST it refuses answers 409, as the page does. This replaces the amendment of 3 November, which expected member removal to lift the gate: a removed member's computers do not need it, since Omnigent's own removal records theirs. A page whose action is not offered answers 409 without a form.
- *Deleting without signing out.* An administrator finishes a pending removal of someone else's computer as before (sign out, then delete its saved files and logins). Where the sign-out cannot settle, because a run was tried and did not finish or a login may have changed after the last save, the administrator may delete it without one (`delete_without_sign_out`, offered by `unsignedDeletionDue` and checked again in WorkspaceDO's write). The page says that the provider sessions are not revoked and that the person or their provider's administrator must revoke them; the platform never claims a revocation it did not see. A computer's owner has the revocation record instead. A failed run is recorded beside the record (`sign-out-failed`), so the previous Worker still reads the record.
- *A removed member's computer whose save keeps failing.* A removal stops a computer only after saving its files and logins. When Omnigent's `terminate` names the computer's owner without a membership (their account is gone), WorkspaceDO records a member removal under a key of its own (`member-removal`) and counts the removal's stops refused because their save failed. After three, as `refusedSleeps` counts sleeps before FH-35's "stop without saving", an owner or admin may stop it without saving; a save being retried gives way to it. It saves the logins first if it can, and if they cannot be published by the credential barrier's deadline it stops anyway and records that a login may be lost, so the removal needs revoking or "delete without signing out". Records and bundles are deleted only once the container has stopped. The computer's owner keeps FH-35's own rule for their computer.
- *"Deleting…" until it is done.* A resolved removal reports its deletions of saved files and logins as under way (`deleting`); the pages say "Deleting…" and keep the computer listed until they finish, then "Removed".
- *Still not here:* per-member device registrations (WP8.5), so there is nothing to revoke there yet; a removal that survives restoring Omnigent's database to before it; and copying a removed member's work to someone else. Their threads stay readable by owners and admins, as before.

### Custody by material

| Material | Intended custody and persistence |
| --- | --- |
| Credential-store encryption keys | Versioned keys held by the platform Worker. The planned signed service binds encryption to record identity; the server holds an HMAC signing credential, not those encryption keys. Ciphertext in SQLite/R2 does not imply plaintext is absent from server memory. |
| Server credentials | Cookie/bootstrap material as applicable, database-replica/artifact storage credentials and private-bridge signing credentials reach the server as required. Native GitHub linking also needs its GitHub App configuration. These are not baked into the image. |
| Claude/Codex logins | Login files on the computer and in the declared credential checkpoint; never ordinary workspace layers. Treat checkpoint read access as access to those logins. |
| Launch, runner-binding and delegated tokens | Runtime memory/environments or narrowly excluded runtime files as appropriate; every live generation must be absent from published workspace layers. No long-lived Omnigent login/refresh grant belongs on a computer. |
| Omnigent login on a personal host | The owner's own machine (amended 31 October 2026): Omnigent's command-line store under that build's data directory, mode 0600, holding a session and its refresh grant. Revoked by the owner's password change. Not a cloud computer, so the row above does not apply. |
| Omnigent-linked GitHub | The server stores encrypted access/refresh material and uses plaintext to refresh/vend. Its refresh token stays on the server. The host's local broker gives git/gh the access token in memory/environment, without a token in helper arguments or gh `hosts.yml`. Unlinking prevents new vends; an already issued token remains valid until expiration or provider revocation. |
| Codex key-provider API key | `provider_key` under `.omnigent/codex-native/<bridge>/`, mode 0600, for the app-server lifetime; referenced by generated configuration and removed on close. The file and `provider_key.*` temporaries are excluded secret families. Saved `config.toml`/profile files retain references, not inline keys. Key providers use `api_key_ref`, not an inline key in the computer's Omnigent configuration. |
| Platform connected accounts | Superseded by [ADR 0008](0008-connected-accounts-omnigent-mcp-registry.md): on the generic MCP path, Omnigent's registry and credential store hold the service login, sealed by the Worker's key service, and agents on computers receive schemas and results rather than the raw credential. This does not keep credentials from an authorized server process: a Cloudflare administrator, or anyone able to execute code on the server, can use server-held credentials. Native GitHub is a deliberate exception described above, and native Claude/Codex logins live on computers and in credential checkpoints. Databricks/other native credential providers remain unconfigured. |

The checkpoint buckets have only Worker-binding access, without a computer S3 token; the server's storage token covers its replica/artifact scope. Version one has no application-level checkpoint encryption. R2 encryption at rest and private access do not protect login files from an account/Worker administrator.

**Credential-entry warning.** A key pasted into a conversation, tool argument, repository file or upload does not enter the encrypted MCP credential store. It can reach model providers, transcripts, artifacts or checkpoints. Connect service keys only through **Settings → MCP**. Native Claude/Codex sign-ins and the native GitHub flow follow their separate custody paths above.

Service destinations remain operator-controlled under the fixed-manifest model. Validation rejects obvious local destinations and Omnigent refuses redirects, but validation does not inspect DNS results. A public-looking name that resolves to a private address is therefore a known limitation; manifests and operator-supplied origins must be reviewed accordingly. An authorized service receives its own credential in the request and must be trusted not to disclose it in its tool results: encryption and destination validation do not sanitize what a service sends back. Making service destinations editable beyond this operator-controlled model needs a fresh review of which destination receives which credential.

## Alternatives and consequences

Blanket claims that containers contain no secrets or runners have only host scope are false. Path blocking alone cannot distinguish runner events from human approval answers. Delegation checks and recorded verdicts preserve approved runner execution while refusing impersonation. The host broker removes disk copies; it deliberately does not deny running code access to GitHub tokens. A Worker key service keeps this installation on Cloudflare; a faux Vault service would add an inaccurate external API contract.
