# 0008 — Connected accounts through Omnigent's MCP registry

Status: accepted design (owner decision D43, 29 October 2026), amended 2 November 2026 (owner decision D57: administrators add MCP servers on Omnigent's page, below). Supersedes ADR 0004's "Platform connected accounts" custody row and its sentence on installation-wide default approval policies for connected accounts. Platform wiring is in source and tested locally; Cloudflare qualification remains.

## Context

The earlier plan built connected accounts on the platform: a Worker connection service with one Durable Object per account, its own vault and operation journal, a gateway on a private host, two core changes in Omnigent to plug it in, and installation-wide default approval policies generated for write tools (ADR 0004). Meanwhile Omnigent gained what that plan provided: an MCP registry of administrator-approved services, a gateway on its own server that holds each account's login and calls the service itself, a settings page to connect, test and disconnect accounts, a per-conversation picker, and policies around every gateway call. Its credential store encrypts through a pluggable cipher, and the platform Worker already serves the key service that cipher needs (ADR 0004, WP5.9). On the platform the registry was simply not switched on, and the cipher was tied to GitHub linking.

## Decision

**Omnigent's server is the gateway.** Connected accounts are Omnigent's own MCP registry: `POST /v1/mcp/{service}` on the server, its credential store, its Settings → MCP page and its picker. The platform builds no gateway, connection service, vault, journal or approval layer of its own, and needs no Omnigent core change for it.

**Custody.** An account's login is a row of Omnigent's credential store, sealed by the platform Worker's key service under the record's own identity; the database and its replica hold only ciphertext, and the record keys never leave the Worker. The server uses the plaintext only in memory, to call the service or refresh the login, and every write to the record (connect, a refresh that rotates the refresh token, disconnect) is acknowledged only once replicated (ADR 0003). No endpoint returns a token, and generic MCP logins are never vended to a host: no connected account's login reaches a computer or a checkpoint. GitHub's native linking remains the one deliberate exception (ADR 0004). The cipher is on whenever the key service's signing pair is set, with or without GitHub, and the installer makes the key service's keys at install.

**Which services (amended 2 November 2026).** The owner asked for "a UI where I can simply add an mcp server", with whatever tokens it needs stored securely and available to the agents (D57). That page is Omnigent's own, built in the fork (WP8.13) as a general feature: an administrator adds a server in Settings → MCP → Add MCP server, with its URL, its login type (none, an API token each member pastes, or OAuth with discovery and dynamic client registration) and the tools agents may use, and it is live without a restart. It is the main path. Omnigent keeps the server in its database and an OAuth client secret in the credential store, sealed under the key service like a login, and only a person signed in as an administrator may change it; a runner's delegated token is refused. The server image builds the registry with Omnigent's service store whenever the key service is on, so the page needs nothing chosen at install; Omnigent's own `OMNIGENT_MCP_ADMIN_SERVICES=0` turns it off.

The services the image ships as manifests, reviewed and released with the code, each with a non-empty tool allowlist and the list of what the installer must ask for (the service's origin, an OAuth client's ID and secret), become the page's presets: starting points for its form, never a secret. A manifest the page cannot take, such as GitHub's MCP server, which uses Omnigent's GitHub link, is still turned on as before: the installation stores only its choices, as Worker secrets that reach the server, the image checks them at every start and makes them registry entries, and the installer's `services` step makes the secrets change, waits for the server's restart and confirms from Omnigent's own `/v1/info`. Any manifest can still be turned on that way. Such a service is read-only on the page and hides a page server of the same name.

**Destination rules (amended 2 November 2026).** The rules are the platform's, wherever a service comes from: `https` only, a public host name (no IP literal, `localhost`, `.internal` or `.local` host, a real top-level domain), no credentials, query or fragment in a URL. For a page server the image passes them to Omnigent as the registry's destination policy, together with Omnigent's own default rules and one more: every address the host resolves to must be public (no loopback, private, link-local or other non-public range). Omnigent applies the policy when a server is saved, to every URL its OAuth discovery and client registration read, and on every connection it opens, which it pins to the address it checked, so a name that later resolves elsewhere is refused. It never follows a redirect for a page server, since a redirect would connect somewhere the check did not see. For a chosen service the image checks the URL rules at every start and refuses to start (exit 78, naming the setting, never its value) on a manifest or choice that breaks one; Omnigent's client does not follow its redirects either, but the MCP SDK's own same-origin redirects stay, as they were. A chosen service's host is not resolved and checked, because only the installer chooses those origins; a page server's is, because any administrator can enter one.

**Changing a page server.** Changing its URL, its login type or any of its OAuth settings deletes every login saved for it, in the same write that changes it: a login is never sent to a destination it was not made for. Members connect again. A change to its title, description, timeout or tool allowlist keeps the logins. Each change to a page server or its allowlist is acknowledged only once replicated, so a restore cannot bring back a removed server, an old address or a tool taken off its list.

**Approvals.** Writes go through Omnigent's policies as they are. No default approval policy is generated, and manifests carry no read/write split for policy purposes. An ask rule can be added in Omnigent later. The approval-bypass risk ADR 0004 records for policies added by runner tokens is unchanged.

**Disconnect** deletes the login; the next call fails at once, and a call already authorized may finish. It does not revoke the grant at the provider. A login the provider rejects shows "Reconnect needed" (above).

## Alternatives and consequences

The platform connection service would have given the same guarantee to computers, logins never on a computer, with far more parts in two repositories. A separate connector container or a hosted MCP portal would add cost or a second gateway in front of Omnigent's.

A page of our own on the platform would have repeated what Omnigent's settings already are, and kept the services in Worker secrets that need a restart for every change. Omnigent's page keeps them where its registry already looks, and the platform contributes only what it knows: its destination rules and its keys.

Consequences:
- A page server, or a change to it, is live at once. A service the installation turns on with the installer, or a change to it, restarts the server once.
- A tool a service adds later stays hidden until an administrator ticks it on the page, or, for a chosen service, its manifest lists it.
- Page servers have OAuth discovery and dynamic client registration; a chosen service has neither. A login the provider rejects is marked rather than silently kept: a 401 to its access token, or `invalid_grant` when it is refreshed, makes Settings → MCP and the picker show "Reconnect needed"; a marked login refreshes before its next use, and nothing is replayed. A fresh connect clears the mark (Omnigent's F1, in the pinned build `afb809aa6`).
- Code on a computer holds a runner's delegated owner token, which Omnigent refuses only under `/auth` and `/oauth`: it can list the catalog and disconnect or replace one of the owner's logins, never read one. The owner accepted this with the rest of an agent's reach on its own computer (decision D44, 30 October 2026): what must not leak are the logins and keys shared with Omnigent, and none of these calls returns one. The computer route therefore blocks none of Omnigent's MCP account endpoints.
- Whoever controls the Worker or the account can use the logins, as for GitHub's.
- The installer cannot read the page's servers, which are in Omnigent's database. An update therefore relies on the server's own record: its restore point notes the page's servers when it is taken, before Omnigent first starts on the new release, and every start in the update's window reports how many of those Omnigent serves, which the watchdog puts on its status line. The update accepts only a restart that serves them all ([ADR 0007](0007-compatible-releases-recovery.md)).
- The page adds a database migration, one way once complete: an earlier server refuses the migrated database, and going back is the update's rollback, inside its window ([compatibility](../compatibility.md#the-mcp-page-2-november-2026)).
- An agent's tool calls, with whatever it puts in them, go to the destinations an administrator chose. The destination rules keep them off private networks, the loopback and link-local addresses such as a cloud's metadata service; what a public destination does with them is the administrator's choice ([data flows](../data-flows.md#connected-services-mcp)).

## Implementation and qualification

Platform main builds [Omnigent's registry](../../images/server/cfo_server/app.py) whenever the key service is on, with Omnigent's service store, the platform's [destination policy](../../images/server/cfo_server/mcp.py), the [shipped manifests](../../images/server/services/) as the page's presets and [the installation's choices](../../images/server/cfo_server/mcp.py) as its services, with the credential store on the [key service](../../worker/src/internal/key-service.ts); the installer's optional `bootstrap.ts services` step stores the choices and waits for the server's report on the watchdog's status line, and `update` requires the restarted server to serve every page server its database held. The page itself is the fork's WP8.13 (`cfo/upgrade-0.20.0` at `dc4cff998`). Version one initially shipped Omnigent's demo OAuth MCP service as the test service and GitHub's MCP server through the GitHub link. Tested in source; in process with a loopback key service and the demo service, as a chosen service and as a page server (discovery and client registration, the client secret and the login sealed, the allowlist, a runner's call, a redirect and private destinations refused, the counts); and, for a chosen service, in a local end-to-end run with the platform Worker's real key service, the server and computer images and the demo service over HTTPS (connect, calls from a computer with the runner's own client, a refresh, disconnect, ciphertext only in the database and its replica, a canary scan of the computer, of what its checkpoint would hold and of every log). Not yet run on Cloudflare: the provider's callback through Access, a computer's private route to the gateway, drops and deploys during a call, a real provider's OAuth client, and a page server end to end with the images.
