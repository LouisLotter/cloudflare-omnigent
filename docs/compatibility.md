The [server Dockerfile](../images/server/Dockerfile) pins source/base inputs and checks the fork Dockerfile mirror. It installs Omnigent's Python dependencies from the fork's lock file, with the fork's `s3` extra (`boto3` and `botocore` at the lock's versions, 1.43.25 at `3d7f7d08c`, unchanged since `184b5cf8b`) for the artifact store in R2. Build arguments may override defaults, so record the values actually used. A matching mirror digest only describes build coupling; it does not mean that different fork commits contain the same fixes. Rebuilds also resolve Debian packages, so source pins alone do not promise identical image bytes.

The computer image pins the same fork commit as the server's default, so a computer's host and the server are built from one source; the selected assembly must still qualify them together.

**The runner disconnect grace (29 October 2026).** The server image sets `OMNIGENT_RUNNER_DISCONNECT_GRACE_S=150`, replacing any value from the environment. Upstream's default is the 90 s runner liveness lease. A computer's tunnel may drop while a save pauses it, and its reconnect is allowed 100 s, so a dropped runner gets 150 s before Omnigent fails its session. The setting is server-side only, and the liveness lease stays 90 s. A reported runner crash, an intentional stop, a removal and the sleep path don't wait for it. The cost is that a computer lost with no crash report fails its sessions up to 60 s later than upstream would. Tested in the image against the pinned fork; not yet measured on staging.

**Certificate trust (27 October 2026).** After the October 2026 compromise of eight eMudhra intermediate CA keys, a client that trusts emSign ECC Root CA - G3 or Sectigo's AAA Certificate Services (through its cross-signs) can be shown a forged certificate for any host. Both images now refuse those chains:

- Each build fails unless Debian's `ca-certificates` is at least `20250419+deb13u1` (trixie, under both runtime stages; the pinned `python:3.12-slim` digest already carries it) and no bundle the image ships holds either root: the system bundle, certifi's, or pip's vendored copy ([trust check](../images/trust/trust_check.py)). The server build also fails unless botocore verifies with certifi's bundle: botocore's fallback still holds AAA Certificate Services.
- Both images install hash-pinned certifi 2026.10.23 and pip 26.2.2 over the fork's lock (since `3d7f7d08c` the lock has certifi 2026.10.19, which drops the emSign root; the images keep the tested 2026.10.23. pip 25.0.1 vendors a certifi with both roots). pip 26.2.2 also replaces the wheel `ensurepip` seeds into every new virtual environment, and the build's trust check also reads bundles inside wheels. The builders install uv from hash-pinned wheels.
- Node 22.23.4, gh 2.103.3 (Go 1.27.3) and Claude Code 2.1.311 also refuse the compromised chains when the roots are explicitly trusted. Codex 0.164.0's rustls client, which it uses only when given a CA bundle of its own, refused them even with the roots in that bundle (rustls-webpki 0.103.16); 0.163.0's connected. Codex's default client (its vendored OpenSSL) and Litestream 0.5.17 (Go 1.25) have no such denylist and rely on the system bundle, so `ca-certificates` stays installed. Claude Code 2.1.302 accepted the emSign chain.
- Claude Code and Codex are installed from npm at exact versions without running package scripts. The build checks each extracted tree (every file and symbolic link, the native binaries included) against a committed digest before Claude Code's own postinstall runs, and again after it.
- On locally built images, the [network probe](../images/trust/tls_probe.py) recorded curl, Python's `ssl`, httpx, requests, botocore, the installed pips and a new virtual environment's, git, Node, gh, Claude Code and Litestream refusing both forged chains with certificate errors, and verifying GitHub, Anthropic, OpenAI and R2 endpoints. Codex prints no cause, so its refusal is inferred, not shown: it connected and got no answer, twice, and with the forged roots added to its own OpenSSL's trust (`SSL_CERT_DIR`) it got the forged server's answer. Against a local server, the same signature came with OpenSSL's "unknown ca" alert from Codex. Deployed images have not been probed.
- Codex 0.164.0 adds two fields to `~/.codex/auth.json` (`tokens.login_owner_id`, `tokens.oauth_provenance`). Its path, mode, in-place write, status output and logout are unchanged, and the platform copies the file as opaque bytes. In local offline checks with synthetic logins, 0.163.0 and 0.164.0 each read, refresh and sign out with the other's file, and a file restored on a second computer stays signed in. Claude Code 2.1.311's login file and sign-in commands are unchanged.
- Signing in from the setup page reads the CLIs' own login output. It is tested against transcripts of Claude Code 2.1.311 and Codex 0.164.0 (Claude's link on `claude.com/cai/oauth/authorize`, Codex's on `auth.openai.com/codex/device` with a four-and-five-character code). A CLI whose output changes fails an attempt as "unexpected", and the page offers the terminal, so a version bump must recapture them. A computer whose supervisor's `hello` names no `sign_in` feature (an image before it) gets the terminal instead of the buttons.

**Runtime and CLI behaviour seen on staging (27 October 2026).** A staging run of the computer image found the following; the fixes are in source and qualified locally (Docker and the Workers runtime), not yet on Cloudflare:

- **Claude Code 2.1.311's fullscreen upsell.** While no settings layer names a renderer (`tui`), Claude Code asks "Try the new fullscreen renderer?" on its first three starts. Omnigent's harness can't answer it, so the first session failed. The computer image now installs `/etc/claude-code/managed-settings.json` (root's, mode 0644) with `{"tui": "default"}`. These managed settings take precedence over the person's and Omnigent's own settings files, so the computer always uses the default renderer. No other startup dialog of 2.1.311 blocks a start the harness drives:
  - Omnigent itself records onboarding as done and the workspace as trusted, and pre-approves project MCP servers.
  - An unanswered Consumer Terms update on the account could still show its dialog.
- **Claude Code 2.1.311 defaults to Auto mode** when no permission mode is set, and Omnigent's harness sets none. Omnigent's policy hooks still run on every tool call. Claude now asks for permission, and so raises Omnigent's approval prompt, only for what Auto mode doesn't decide itself.
- **`durable_object` containers.** The hostname, the Durable Object's 64-character ID, is not in `/etc/hosts`, so `sudo` warned on every call. `/` was owned by uid 2346, not root (the image's own layers give it to root), so Claude Code refused every directory for its cross-session messaging sockets and turned that messaging off. Claude Code checks every directory up to `/`, so `CLAUDE_CODE_TMPDIR` and `XDG_RUNTIME_DIR` don't help. The supervisor, as root at start, gives `/` back to root. The hostname can't be mapped: on these containers `/etc/hosts` is a read-only overlay mount (seen on 28 October). So the image resolves the machine's own name through NSS `myhostname` (Debian's `libnss-myhostname`, pinned; `hosts: files myhostname dns`). The supervisor checks at start that the name resolves, and maps it in `/etc/hosts` only where it doesn't and the file is writable. The status page reports whether the name resolves. Both changes are idempotent and best-effort.
- **Runner environment.** Omnigent's host passes a runner only an allowlist of its environment. That allowlist left out the image's Claude Code settings (telemetry, error reporting and updates off). The supervisor now names those settings in the host's `OMNIGENT_RUNNER_ENV_PASSTHROUGH`.
- **Sandbox SDK 1.0.0 retries nothing.** Its shim uploads each part once, and when R2 fails a part, its gateway answers 502 with R2's message. One lost connection ("Network connection lost.") therefore failed a whole save. WorkspaceDO now repeats the whole upload after a transient failure: a 502, 503 or 504 from the gateway, or a lost or reset connection. It tries twice more, after 5 s and then 15 s, within the same upload deadline. A failed attempt leaves no object, and only the attempt that returns a record is published.

**Tolerant status readers (29 October 2026).** After a platform rollback, an older WorkspaceDO can meet a newer computer supervisor until that computer next stops. A strict reader refused the supervisor's whole `computer_status` reply for one name it did not know, such as a new hostname state or a new field, so the status panel said the computer did not answer and the status log backed off. That reply is informational: it changes no state. So from this release on, its readers degrade instead of refusing:

- a field they do not know, at any depth, is dropped, never passed on, so no text from the computer leaves through one;
- an enum value they do not know becomes the field's "can't tell" value: `unknown` for the CLIs' logins, the sign-in states and the hostname, and `other` for an alert's kind; alerts read as `other` are added together.

Adding a status field or enum value is therefore safe both ways: an older reader parses a newer supervisor's status, and a newer reader parses an older one's, as long as the reader treats every added field as optional, as it does `terminals`. A field added as required would refuse an older supervisor's status. A reader from before this release still refuses a newer status whole, so this protects rollbacks to this release or later. Removing or retyping a field, a value of the wrong type, a malformed version or an out-of-bound count still fail the read. Everything else on the computer API stays strict, because it carries or changes state: commands, the other command replies, reports, credential checkpoints, captures and sign-in refuse an unknown field or value. The exported JSON Schema shows what a read yields, which is what a supervisor of this release sends, so the supervisor's own outbound check stays strict. The contract's `tolerated/` fixtures pair a newer supervisor's reply with what a reader makes of it. The setup page's own copy of the status is not parsed again by the web Worker, and its labels show a name they do not know as "not known".

Current [CI](../.github/workflows/ci.yml) runs the workspace's Node checks, the root `python/` project, limited canary checks, explicit platform and [web](../worker/wrangler.web.jsonc) bundles, and builds/tests the existing server image targets and the computer image's `computer` and `test` targets, with its in-image suite. Its image suite excludes S3/fault integration and runs without external networking. The [scripts test configuration](../scripts/vitest.config.ts) already includes restore-drill staging tests in Node with fakes. Restore-drill Python and real-platform qualification remain separate; the added CI checks do not change the source pins or assembly status above.

The [canary scanner](../scripts/canary-scan.ts) detects synthetic markers and exact configured values in its supported paths/formats. A clean result is bounded evidence about those values; it is not general proof of no credentials, a whole-repository/history/image scan, or publication approval. Incomplete scans fail.

For every qualification run record platform and fork revisions, actual Worker build/deployment IDs, final server/computer manifest digests and architecture, CLI/SDK/Litestream versions, packaged contract/policy assets, test commands/results, known exclusions and remaining runtime obligations. Image IDs from local tests must be labelled separately from registry manifest digests. Do not use mutable “latest” tags as the record.

## Keeping the pinned tools current

The images pin every tool exactly, and no CLI updates itself on a computer: the computer image turns Claude Code's updater off (`DISABLE_AUTOUPDATER`, `DISABLE_UPDATES`) and Codex's startup check off (its managed settings). A new version arrives in three steps:

1. **A daily pull request.** The [tool version check](../.github/workflows/tool-versions.yml) ([scripts/tool-versions](../scripts/tool-versions/)) runs every day. It looks for newer releases of Claude Code, Codex, gh and ttyd, new digests of the `python:3.12-slim` and `node:22-slim` base images (they bring Debian's security fixes), and newer certifi, pip and uv. It opens one pull request that bumps them all, on the branch `automation/tool-versions`, or updates that pull request if it is still open, and runs CI on it. The owner merges it once CI is green.
2. **`node scripts/bootstrap/bootstrap.ts update`** deploys the new release to an installation ([updating](install.md#updating-your-installation)).
3. **Each cloud computer** takes the new image at its next start or wake.

The workflow computes every checksum itself and never takes one from a pull request. What each check shows:

- **Claude Code and Codex (npm).** npm checks each package against the registry's SHA-512 integrity value. `npm audit signatures` then checks the registry's signature over those values and Codex's provenance attestation, which says which GitHub workflow built it. Claude Code publishes no provenance, so its evidence is the registry's signature: the registry served what was published, not who built it. The computer Dockerfile's own install stage records the installed trees' digests, and every image build installs again and must match them.
- **gh and ttyd (GitHub releases).** The download's SHA-256 must match the line for it in the release's own checksum file, and GitHub's upload digest. That shows the file is the one the release published.
- **certifi, pip and uv (PyPI).** PyPI's SHA-256 of each file; pip's `--require-hashes` checks every download in the build.
- **Base images (Docker Hub).** The digest the official tag points to, checked against the manifest's bytes. The pull request names the Python or Node version inside. It says which image this is, not that it is sound: CI's builds and tests are the check.

There is no minimum release age: the owner decided against a cooldown, so a release is proposed the day it appears, and CI and the owner's review are the gate. A bump the owner closes unmerged is not proposed again until a newer release changes it. Not checked automatically: Litestream (its version is tied to the server's tested replication behaviour, so it is raised by hand), the Omnigent commit (the fork's own process), the Sandbox SDK image, Wrangler and the `@cloudflare/*` packages, and Debian's tmux and libnss-myhostname. A Claude Code or Codex bump does not capture the sign-in transcripts again ([testing](testing.md)); the pull request says so.
