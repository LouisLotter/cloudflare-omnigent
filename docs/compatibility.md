## Support access for owners and administrators (5 November 2026)

WP8.15 (owner decision D62) lets every team owner and administrator manage other people's cloud computers from their pages: the page, its status, a wake through Omnigent, the terminal, the size and Stop. Sign-ins stay the person's own ([ADR 0004](decisions/0004-identity-credential-authority.md)). The supervisor, its protocol, the launcher protocol, the manifests and the checkpoint keys are unchanged.

- **The page state.** `ComputerPageState` gains an optional `ownerMemberId`, the binding's team member ID, in an administrator's view only (for the link to the person's page in Omnigent). An administrator's state now carries the terminal's window, and still no `signIn`.
- **WorkspaceDO's storage.** Unchanged in format. The operation journal's entry for a page action keeps its strict shape (`fingerprint`, `outcome`, `at`); the actor (`member:<id>` or `installation`) is recorded inside the outcome, which the entry already keeps as an opaque value. The fingerprint leaves the actor out, so it is the same as before; a repeat answers without the actor.
- **The server image** passes `admin_support_access=True` to `create_app`, which only a fork build with WP8.15's fork part accepts. That build is the server's Omnigent pin from this release on; with an earlier pin the server does not start.

| Pair during an update | Result |
|---|---|
| **Platform Worker downgrade:** the previous platform Worker on storage this one wrote, as `update --rollback` leaves it | Works. The previous Worker parses the journal's entries as before; a repeat of a page action this one recorded returns its outcome with an extra `actor` field, which the loose `PagesResult` the web Worker reads lets through and nothing reads. While it runs, administrators have the fleet card's actions only, as before WP8.15 |
| New web Worker, WorkspaceDO before WP8.15 | Works with less: an administrator's computer page opens, but the older page front refuses its status, terminal and size (`forbidden`), and the page has no link to the person's Omnigent page |
| Web Worker before WP8.15, new WorkspaceDO | Works as before WP8.15: the older pages answer an administrator's computer page as not found and ignore the new state fields |
| New Worker, server whose Omnigent build refuses an administrator's start | Works but for the wake: an administrator's wake from the page is refused, and the page says so ("Omnigent did not let your account wake this computer"); the terminal of a computer already awake opens |
| Computer image of either release | Unchanged: the supervisor never sees who opened the terminal |

These pairs are read from the source. The downgrade is tested by reading a page action's journal entry this controller wrote with the previous release's own storage schema, and its replay with `PagesResult` ([its reader](../worker/test/fixtures/previous-worker/README.md)); the other pairs are not run.

## Sharing, and nothing public (4 November 2026)

Both images moved from `922b69c62` to `f53990a30` on `cfo/teams`: WP8.10's fork part merged in, with no migration and no change to the fork's Dockerfile, entrypoint, `pyproject.toml` or `uv.lock`. The server image's own settings changed with it.

- **Sharing between members is on.** The image's default sharing mode is now `on`, Omnigent's own default (owner decision D51), where it was `off`: a session's owner can give another member Read or Edit. `SERVER_ENV_OMNIGENT_SHARING_MODE` can still narrow it to `read_only`, `restricted_read_only` or `off`. An installation that set none gets sharing at the server's restart with this release.
- **Nothing public, pinned.** Public sharing ("anyone with the link") is pinned off, at the read level, as default-public sessions already were. `OMNIGENT_PUBLIC_SHARING` other than `off`, or `OMNIGENT_PUBLIC_SHARING_MAX_LEVEL` other than `read`, makes the server refuse to start (exit 78), with a message that names the setting and the rule but never the value; it was a setting that defaulted to off. A public grant stored while an older image allowed public sharing gives nobody access: the image starts Omnigent with `public_grants_when_disabled="ignored"` (a new `create_app` option; Omnigent's default, `"honoured"`, keeps such grants working after public sharing is turned off), and keeps the rows.
- **An update that meets the pin can still go back.** An installation that had set `OMNIGENT_PUBLIC_SHARING_MAX_LEVEL=edit`, say, is refused by the new image. Inside the update's window the new server first takes its restore point, or carries out a rollback order, and only then refuses, so `update --rollback` goes back as usual. `update` stops at once with exit 1 when the new server refuses a setting, and `bootstrap.ts run` too, instead of waiting out their deadlines; the watchdog says `config_held` at every check of such a hold, and `status --logs` tells a current hold from a past one ([troubleshooting](operations/troubleshooting.md#a-server-that-refuses-a-setting)).
- **The computers overview.** A persistent provider may declare an overview page (`PersistentHostPolicy.overview_url`), listed in `/v1/info` as `persistent_host_overview_urls`. The Cloudflare launcher declares the path `/platform/computers`, and Omnigent links it for everyone, as a "Computers page" row in the sidebar's top links and in Settings → Computers ("Your computers' setup, sign-ins and terminals are on the computers page"), and for owners and administrators also as "Other people's computers are on the computers page". The web app keeps only a page that resolves to its own origin over HTTP(S), with no userinfo, backslash or control character. A server on an earlier pin lists none, and the web app then shows no link.
- **Wording.** The Share dialog says, when Edit is offered, that someone with Edit runs turns on the session's computer with its owner's subscription; an invitation that cannot be used gets one plain answer that says what to do; the invitation page points a new member to Settings → Computers; the reset-password dialog and the sign-in refusal read more plainly.

| Pair during an update | Result |
|---|---|
| New server, previous computer image | Works: the host protocol and the launcher's calls are unchanged |
| Previous server (a rollback inside the window), new computer image | Works, as above |
| New web app, previous server | No overview link (the field is absent); everything else as before |

## The team model (3 November 2026)

Both images moved from `9be778d79` on `cfo/upgrade-0.20.0` to `922b69c62` on `cfo/teams`, the team model merged onto it (owner decision D50): memberships and roles (WP8.1), authority re-checked on open connections and machine credentials (WP8.2a, 8.2b), the owner context the launcher's version 2 names (WP8.4's fork part), approver roles (WP8.6), the display-only team view (WP8.8, D59), a front proxy's sign-in bound to members with invitations and suspension (WP8.3), and what the move behind Access checks with (WP8.11's fork part, D60): the team's binding state (`omnigent.server.team_status`, counts and host IDs only), a bind mode that binds without refusing anyone, and the founding owner's binding taken only from a browser's own sign-in (a CLI login, which asks for refresh material, gets its token in the body and no cookie). The fork's Dockerfile (mirror digest `dca1880e5`), its Docker entrypoint, `pyproject.toml` and `uv.lock` are unchanged.

**The database.** Five additive migrations run in order when the new server starts, inside the update's read-only window and after its restore point: `tm1a2b3c4d5e` (the team; the one account with the administrator flag becomes its active owner, nothing else changes), `ri1a2b3c4d5e` (the host sandbox a runner was bound into; runner bindings on cloud computers are retired, so each of their threads binds a new runner at its next launch, while personal hosts' bindings stay), `ap1a2b3c4d5e` (approver grants, protected policies and the approval ledger), `at1a2b3c4d5e` (WP8.8's) and `ti1a2b3c4d5e` (invitations, a binding's verified address, the admission revision, the founding member). Each is one way once complete; `update --rollback` inside the window goes back with the restore point. The [rehearsal](operations/teams.md#1-rehearse-on-a-copy-of-the-database) runs them on a copy first.

**Off until moved.** With the platform's defaults the server's identity mode is `off`, no envelope is signed, ingress pins the owner and the team page shows a team of one. The launcher sends version 2 from this pin on, naming each computer's owner, and WorkspaceDO adopts every existing computer for the installation's owner at its first version 2 call ([computers bound to one owner](#computers-bound-to-one-owner-3-november-2026)).

| Pair during an update | Result |
|---|---|
| New server, previous computer image | Works for existing threads; a new runner launch on a cloud computer needs the computer restarted on the new image (as with every 0.20.0 pin) |
| New server, personal host on the previous build | Works: the host protocol is unchanged; set the host up again at a convenient time |
| Previous server (a rollback inside the window), new computer image | Works: the computer's host and supervisor are unchanged for the previous server |

**The move behind Access.** From this pin on, `bootstrap.ts update --team-admission members` moves an installation ([moving an installation to a team](operations/teams.md)): the update in bind mode with its restore point, the owner's browser sign-in, required mode, then members admission and the Access application's member group. Its stage is kept with each update's previous release, so `update --rollback` puts it back as that release had it. With a pin that lacks WP8.11's fork part the installer refuses the move and changes nothing.

## Removing a team member (4 November 2026)

WP8.9 (owner decisions D50, D54) adds member removal: Omnigent's own part is in the fork, and the platform's in the pages and WorkspaceDO ([ADR 0004](decisions/0004-identity-credential-authority.md), [the team's operations](operations/teams.md)). Both images moved from `f53990a30` to `e379f42d5` on `cfo/teams`: WP8.9's fork part merged in, then `openapi.json` regenerated for WP8.10's overview URLs, with one additive migration and no change to the fork's Dockerfile, entrypoint, `pyproject.toml` or `uv.lock`.

- **The fork.** Removing a member is one database transaction with a record of it, in two new tables (`team_member_removals`, `team_member_removal_items`; migration `rm1a2b3c4d5e` after `ti1a2b3c4d5e`, additive, its downgrade dropping only the two tables). The server image passes `OMNIGENT_INSTALLATION_OWNER`, the installer-named owner account, which the team never removes. A removal's computers step links the computers overview that WP8.10 declares (`overview_url`, `/platform/computers`); the image declares nothing new for it. The image's `test` target expects `rm1a2b3c4d5e` as the migration head, so a pin without the fork's removal fails there, not at start.
- **The pages.** `PagesCall` and `PagesResult` gain `delete_without_sign_out`, and the page state's `removal` an optional `signOutFailed`. A page that does not offer its action answers 409 instead of 200, and so does a POST that WorkspaceDO refuses as not offered (before, a redirect with a notice). "No contact" now counts only while a computer is awake: an asleep or stopped computer no longer shows "not connected to Omnigent", its notice or the page's Remove after an hour, for its owner or an administrator. An older WorkspaceDO still counts it asleep; `update` deploys the platform Worker first, so the pages see the new answer.
- **WorkspaceDO's storage.** The record keeps exactly its earlier shape. When a sign-out run ends without a verified sign-out, a key of its own (`sign-out-failed`) records when; a new run and the removal's wipe delete it. A removal Omnigent made for a removed member is recorded under `member-removal`, with its refused stops; the wipe deletes it.
- **The page state's `removal`** also gains optional `memberRemoved`, `refusedStops` and `deleting`. An administrator may send `stop_without_saving` for someone else's computer, accepted only for such a removal after three refused stops.

| Pair during an update | Result |
|---|---|
| **Platform Worker downgrade** on storage this one wrote | Works: the previous Worker never reads `sign-out-failed`, and the record has its old shape. Its pages no longer offer deleting without a sign-out |
| New web Worker, WorkspaceDO before WP8.9 | The page state has no `signOutFailed`: the pages read a run left at `requested` or `tombstoned` instead, and an older WorkspaceDO refuses `delete_without_sign_out` as a malformed call (the page says the computer could not be reached) |
| Web Worker before WP8.9, new WorkspaceDO | Works: it never sends the new call and ignores the new field |
| Server image before WP8.9 with this platform | Works as before: Omnigent's account deletion still terminates the deleted account's computers |

These pairs are read from the source; the new call, the field and the key are tested in the Workers runtime and the controller's simulation.

## Codex sessions get Omnigent's tools from the start (3 November 2026)

Both images moved from `dc4cff998` to `9be778d79` on `cfo/upgrade-0.20.0`, which adds one fork change and nothing else: WP3.52, the order in which a codex-native session starts. The fork's Dockerfile (mirror digest `dca1880e5`), its Docker entrypoint, `pyproject.toml` and `uv.lock` are unchanged. There is no database migration and no interface change.

**What was wrong.** Omnigent gives a native Codex session its tools (its own tools and the MCP servers switched on for the session) through one MCP server, `omnigent`, which serves the list the runner writes to the session's `tool_relay.json`. The runner wrote that list only after Codex's terminal had started. Codex 0.166 starts its MCP servers when the terminal starts its thread, lists their tools once, and does not act on `tools/list_changed`. When its one listing came before the runner's file, the session had none of Omnigent's tools for its whole life, though each tool was ready on the server. Claude sessions were not affected. The cause is upstream Omnigent code, unchanged on its `main`.

**What changed.** The runner starts the tool relay, and so writes the list, before it starts Codex's app server and terminal. The code is in the runner, so it applies on whichever host runs the session: a cloud computer once it starts on the new image, a personal host once its setup is run again.

| Pair during an update | Result |
|---|---|
| New server, previous computer or personal host | Works as before, including the race: a new Codex session there can still start without Omnigent's tools until the host runs the new build |
| Previous server, new computer or personal host | Works: the server side is unchanged |

A tool or MCP server switched on for a Codex session that is already running still does not reach it, because Codex does not list again; start a new session. Going back to `dc4cff998` needs no restore point for this change, since nothing stored changed.

## Computers bound to one owner (3 November 2026)

WP8.4 (owner decision D50) adds launcher protocol version 2 and the page person; nothing in either image changes but the Cloudflare launcher, which the server image packages ([architecture](architecture.md#boundaries-that-must-survive-implementation), ADRs [0001](decisions/0001-omnigent-owns-host-execution.md), [0004](decisions/0004-identity-credential-authority.md) and [0005](decisions/0005-checkpoint-publication-continuation.md)). The supervisor, its protocol, the manifests and the checkpoint keys are unchanged.

- **The launcher.** Version 2 is version 1 with `owner` on every call but `prepare`. The Cloudflare launcher sends it only when Omnigent passes `owner=`, which only a build with the fork's `owner_context` capability does (`cfo/teams`, from `84a528a2a`). The pin before `922b69c62` (`9be778d79`) had no such capability, so its server sent version 1; from `922b69c62` on, main's server sends version 2 and every existing computer is adopted for the installation's owner at its first call.
- **WorkspaceDO's storage.** The computer's record keeps exactly its earlier shape. The owner binding and the two pointer stamps are under a key of their own (`ownership`), written in the same transaction as the record, and only once there is something to keep: an installation whose server sends version 1 never gets the key. Storage written before WP8.4 reads as unbound (the installation owner's) with unstamped pointers.
- **The pages.** `PageOwner` gains an optional `person` and the page state optional `access` and `ownerName`; the request-intent token now also covers the person, so a page left open across the release asks to be reloaded once.

## The MCP page (2 November 2026)

Both images moved from `0116b9f53` to `dc4cff998` on `cfo/upgrade-0.20.0` (now [`9be778d79`](#codex-sessions-get-omnigents-tools-from-the-start-3-november-2026)), which adds one fork change and nothing else: WP8.13, Omnigent's own page for adding MCP servers (owner decision D57). The fork's Dockerfile (mirror digest `dca1880e5`), its Docker entrypoint, `pyproject.toml` and `uv.lock` are unchanged. No host, runner or onboarding code changed: the computer image differs only in the commit it records. The server image builds the registry differently (below); every other interface it calls is unchanged.

**What the fork adds.** Administrators add, change and remove MCP servers in Settings → MCP → Add MCP server while the server runs: a name, the URL, the login type (none, an API token each member pastes, or OAuth with discovery and dynamic client registration), then the tools agents may use, listed with the administrator's own login. Omnigent keeps them in its database beside the registry file's services (`McpServiceStore`), an OAuth client secret sealed in the credential store under its reserved owner `__mcp_service__`, and serves them under `/v1/mcp-registry/admin/` to a person signed in as an administrator only (a runner's delegated token gets 403). `McpRegistry` takes a `service_store` and a `destination_policy`, checked when a service is saved and on every connection it opens for one, and it never follows a redirect for these services. `McpRegistryConfig.services` is optional, and `presets` lists starting points for the form. Changing a service's URL, login type or OAuth settings replaces its credential version and deletes its saved logins in the same transaction. `OMNIGENT_MCP_ADMIN_SERVICES=0` turns the page off. The platform Worker's key service needs no change: the new records are sealed under their identities like any other.

**What the server image does with it** ([ADR 0008](decisions/0008-connected-accounts-omnigent-mcp-registry.md)). It builds the registry whenever the key service is on, with the service store and the platform's destination rules as the policy, so the page is there with no service chosen. The shipped manifests the page can take (OpenRouter's, the demo service) are its presets; GitHub's, which uses Omnigent's GitHub link, is not, and stays a `services add` choice. A service turned on with `services add` is read-only on the page and hides a page server of the same name. Writes to the page's servers and their tool allowlists are held by the response barrier until replicated, as logins are. The update's restore point records the page's servers the database held before Omnigent first starts on the new release (their IDs, in its manifest); each start in the window compares what Omnigent then serves with that record, the watchdog puts both counts on its status line, and the update accepts only a restart that serves them all. A restore point taken by an earlier image records none, and its window's update then says the count is unknown (roll back and update again).

**The database.** The fork adds migration `mr1a2b3c4d5e` after `c0201a2b3c4d`: two tables (`mcp_registry_services`, `mcp_registry_service_tools`) and an index on `connections`, additive and without a secret column. The server runs it at its first start on `dc4cff998`, after restoring its replica and taking the update's restore point, inside the crash-safe upgrade of WP3.40c. A `0116b9f53` server started on the migrated database afterwards refuses it before writing anything: its start reads the database's revision, does not know `mr1a2b3c4d5e`, and stops with "Omnigent database schema is newer than this version of Omnigent (found revision 'mr1a2b3c4d5e', latest supported revision 'c0201a2b3c4d')" (`_verify_db_revision_is_supported`, before any migration or store opens). **Tolerant status readers (29 October 2026).** After a platform rollback, an older WorkspaceDO can meet a newer computer supervisor until that computer next stops. A strict reader refused the supervisor's whole `computer_status` reply for one name it did not know, such as a new hostname state or a new field, so the status panel said the computer did not answer and the status log backed off. That reply is informational: it changes no state. So from this release on, its readers degrade instead of refusing:

- a field they do not know, at any depth, is dropped, never passed on, so no text from the computer leaves through one;
- an enum value they do not know becomes the field's "can't tell" value: `unknown` for the CLIs' logins, the sign-in states and the hostname, and `other` for an alert's kind; alerts read as `other` are added together.

Adding a status field or enum value is therefore safe both ways: an older reader parses a newer supervisor's status, and a newer reader parses an older one's, as long as the reader treats every added field as optional, as it does `terminals`. A field added as required would refuse an older supervisor's status. A reader from before this release still refuses a newer status whole, so this protects rollbacks to this release or later. Removing or retyping a field, a value of the wrong type, a malformed version or an out-of-bound count still fail the read. Everything else on the computer API stays strict, because it carries or changes state: commands, the other command replies, reports, credential checkpoints, captures and sign-in refuse an unknown field or value. The exported JSON Schema shows what a read yields, which is what a supervisor of this release sends, so the supervisor's own outbound check stays strict. The contract's `tolerated/` fixtures pair a newer supervisor's reply with what a reader makes of it. The setup page's own copy of the status is not parsed again by the web Worker, and its labels show a name they do not know as "not known".

The [scripts test configuration](../scripts/vitest.config.ts) already includes restore-drill staging tests in Node with fakes. Restore-drill Python and real-platform qualification remain separate; the added CI checks do not change the source pins or assembly status above.

The [canary scanner](../scripts/canary-scan.ts) detects synthetic markers and exact configured values in its supported paths/formats. A clean result is bounded evidence about those values; it is not general proof of no credentials, a whole-repository/history/image scan, or publication approval. Incomplete scans fail.

For every qualification run record platform and fork revisions, actual Worker build/deployment IDs, final server/computer manifest digests and architecture, CLI/SDK/Litestream versions, packaged contract/policy assets, test commands/results, known exclusions and remaining runtime obligations. Image IDs from local tests must be labelled separately from registry manifest digests. Do not use mutable “latest” tags as the record.

## Upgrading across a database migration (Omnigent 0.20)

Omnigent migrates its SQLite database when its server starts, and some migrations are one way: once an Omnigent 0.20 server has migrated a database, a 0.19 server refuses it. So an upgrade like that is [ADR 0007](decisions/0007-compatible-releases-recovery.md)'s case, and since WP3.41 every `bootstrap.ts update` handles it, whatever release it comes from (the restore point and the window are the new release's, not the old one's):

1. Before the new server writes, it copies the replica's objects to a restore point beside the replica (server-side copies, 32 at a time, then a manifest with the restored database's SHA-256). Omnigent, and with it the migration, starts only once the restore point exists. A start that runs out of time leaves its copies, and the next start copies only what is missing, so a large replica still gets its restore point over a few starts.
2. From the moment the platform's object runs the new version until the update accepts it, Omnigent takes no request, from the browser or a computer, starts no computer and runs no scheduled task.
3. The update accepts the release once the server answers with a durable owner, still shows on the integrations the installation set up (GitHub linking, MCP services), and has reported the restore point; acceptance restarts the server once without the window. From then on, problems are fixed forward: going back would need the destructive recovery of [the recovery guide](operations/recovery.md#rollback-and-destructive-restore).
4. Until then, `bootstrap.ts update --rollback` puts the restore point back and deploys both Workers' previous versions again; the 0.19 server restores the database exactly as it left it.

What is qualified: the image's restore point and rollback against a file replica and an S3 stand-in with the pinned Litestream 0.5.17 (a restore of the copy is byte-identical to the original restore), the platform's window and holds in the Workers runtime, the installer's state machine against a fake Cloudflare with an interruption at every call and journal write, and a local end to end with the real watchdog and the server image. On Cloudflare (2 November 2026), a replica of 1539 objects copied one at a time and started over at each attempt never finished within the 300 s deadline, so the update's server never started and the update was rolled back; copies now run in parallel and resume. Not yet run on Cloudflare: R2's server-side copies at scale with that change, a version rollback of a container-backed Worker (`cf workers deployments create` forced past the update's secrets), and the restore point's time on a large database, which counts against the start's restore allowance.

## Keeping the pinned tools current

The images pin every tool exactly, and no CLI updates itself on a computer: the computer image turns Claude Code's updater off (`DISABLE_AUTOUPDATER`, `DISABLE_UPDATES`) and Codex's startup check off (its managed settings). A new version arrives in three steps:

1. **A daily pull request.** The [tool version check](../.github/workflows/tool-versions.yml) ([scripts/tool-versions](../scripts/tool-versions/)) runs every day. It looks for newer releases of Claude Code, Codex, gh and ttyd, new digests of the `python:3.12-slim` and `node:22-slim` base images (they bring Debian's security fixes), and newer certifi, pip and uv. It opens one pull request that bumps them all, on the branch `automation/tool-versions`, or updates that pull request if it is still open, and runs CI on it. When main moves on, the next run rebuilds the branch on it with the same bump, so the pull request never stays in conflict with main. The owner merges it once CI is green.
2. **`node scripts/bootstrap/bootstrap.ts update`** deploys the new release to an installation ([updating](install.md#updating-your-installation)).
3. **Each cloud computer** takes the new image at its next start or wake.

The workflow computes every checksum itself and never takes one from a pull request. What each check shows:

- **Claude Code and Codex (npm).** npm checks each package against the registry's SHA-512 integrity value. `npm audit signatures` then checks the registry's signature over those values and Codex's provenance attestation, which says which GitHub workflow built it. Claude Code publishes no provenance, so its evidence is the registry's signature: the registry served what was published, not who built it. The computer Dockerfile's own install stage then installs the CLIs as the image does; before anything from them runs, each CLI and its linux-x64 part (the native binary) must be, file for file, the audited package, and their integrity values must be the ones the workflow read from the registry itself. That stage records the installed trees' digests, and every image build installs again and must match them.
- **gh and ttyd (GitHub releases).** The download's SHA-256 must match the line for it in the release's own checksum file, and GitHub's upload digest where GitHub records one (gh's releases have it; ttyd's 2024 release does not). That shows the file is the one the release published.
- **certifi, pip and uv (PyPI).** PyPI's SHA-256 of each file; pip's `--require-hashes` checks every download in the build.
- **Base images (Docker Hub).** The digest the official tag points to, checked against the manifest's bytes. The pull request names the Python or Node version inside. It says which image this is, not that it is sound: CI's builds and tests are the check.

There is no minimum release age: the owner decided against a cooldown, so a release is proposed the day it appears, and CI and the owner's review are the gate. A bump the owner closes unmerged is not proposed again until a newer release changes it. Not checked automatically: Litestream (its version is tied to the server's tested replication behaviour, so it is raised by hand), the Omnigent commit (the fork's own process), the Sandbox SDK image, Wrangler and the `@cloudflare/*` packages, and Debian's tmux and libnss-myhostname. A Claude Code or Codex bump does not capture the sign-in transcripts again ([testing](testing.md)); the pull request says so.
