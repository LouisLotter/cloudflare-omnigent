The [server Dockerfile](../images/server/Dockerfile) pins source/base inputs and checks the fork Dockerfile mirror. It installs Omnigent's Python dependencies from the fork's lock file, with the fork's `s3` extra (`boto3` and `botocore` at the lock's versions, 1.43.25 at `3d7f7d08c`, unchanged since `184b5cf8b`) for the artifact store in R2. Build arguments may override defaults, so record the values actually used. A matching mirror digest only describes build coupling; it does not mean that different fork commits contain the same fixes. Rebuilds also resolve Debian packages, so source pins alone do not promise identical image bytes.

The computer image pins the same fork commit as the server's default, so a computer's host and the server are built from one source; the selected assembly must still qualify them together.

**0.20.0 rollout boundary.** The server and computer use host frame protocol 1, but a new runner needs the computer's `runner_replacement_targets` capability. The server refuses a launch on a connected computer that does not advertise it with `runner_capability_mismatch` (HTTP 503), before launch admission, binding rotation, Stop dispatch or Git-session creation. The error tells the person to update and restart the computer's host. Existing connected runners may continue; a new session, runner switch, relaunch or `/clear` path that needs a new runner cannot proceed on the old computer. Deploy the compatible computer image and restart affected computers before allowing new runner launches. Do not silently retry the refused operation against another runner.

This installation requires the paired fork host build for new runner launches. Stock upstream 0.20.0 handles explicit replacement targets but does not advertise this fork's capability, so it is also refused. Updating to the stock package alone does not satisfy the gate; the operator must supply the compatible computer image or host build. The `refresh_harnesses` capability is not an acceptable substitute: it existed before upstream added explicit replacement-target handling. Version strings and unrelated capabilities therefore do not bypass this admission check.

| Pair during an upgrade | Compatibility contract |
|---|---|
| Current Worker / previous server | The platform control and replication interfaces remain unchanged. A new Worker does not itself upgrade the server's database or host code |
| Current Worker / previous computer | Supervisor protocol 1 and the existing command shapes remain supported. An unchanged supervisor protocol does not imply support for the new host runner-replacement capability |
| New server / previous computer | Existing runners can remain connected; new runner launch is explicitly refused before effects until the computer's host is updated and restarted |
| Previous server / new computer | The old server can read the additive host capability list. A legacy launch frame without explicit replacement targets keeps the host's existing session-based replacement fallback. This wire compatibility does not establish database rollback safety |

Local checks used the previous packaged `3d7f7d08c` images and the upgrade images: the previous server passed the current platform runtime suite; both supervisor receivers accepted the current Worker command corpus and refused a future protocol; the new server refused a launch for an old computer before admission while retaining its connection and runner list; the old server accepted the new hello, and the new computer decoded the legacy launch fallback. These checks exercise packaged receivers, not full mixed-version Worker journeys or continuation of a running provider turn. Those journeys remain required before rollout.

The upgrade adds a merge migration joining the earlier fork and upstream migration heads. After the upgraded server writes to the database, switching its image back is not a rollback procedure: preserve the pre-upgrade replica/checkpoints and qualify recovery in maintenance mode. Restoring state does not undo external side effects. The existing workspace, credential and checkpoint-policy formats remain at version 1; the RC-53 writer fixture changes for upstream lock files and tool metadata, without adding credential families.

**Certificate trust (27 October 2026).** After the October 2026 compromise of eight eMudhra intermediate CA keys, a client that trusts emSign ECC Root CA - G3 or Sectigo's AAA Certificate Services (through its cross-signs) can be shown a forged certificate for any host. Both images now refuse those chains:

- Each build fails unless Debian's `ca-certificates` is at least `20250419+deb13u1` (trixie, under both runtime stages; the pinned `python:3.12-slim` digest already carries it) and no bundle the image ships holds either root: the system bundle, certifi's, or pip's vendored copy ([trust check](../images/trust/trust_check.py)). The server build also fails unless botocore verifies with certifi's bundle: botocore's fallback still holds AAA Certificate Services.
- Both images install hash-pinned certifi 2026.10.23 and pip 26.2.2 over the fork's lock (since `3d7f7d08c` the lock has certifi 2026.10.19, which drops the emSign root; the images keep the tested 2026.10.23. pip 25.0.1 vendors a certifi with both roots). pip 26.2.2 also replaces the wheel `ensurepip` seeds into every new virtual environment, and the build's trust check also reads bundles inside wheels. The builders install uv from hash-pinned wheels.
- Node 22.23.4, gh 2.103.3 (Go 1.27.3) and Claude Code 2.1.311 also refuse the compromised chains when the roots are explicitly trusted. Codex 0.164.0's rustls client, which it uses only when given a CA bundle of its own, refused them even with the roots in that bundle (rustls-webpki 0.103.16); 0.163.0's connected. Codex's default client (its vendored OpenSSL) and Litestream 0.5.17 (Go 1.25) have no such denylist and rely on the system bundle, so `ca-certificates` stays installed. Claude Code 2.1.302 accepted the emSign chain.
- Claude Code and Codex are installed from npm at exact versions without running package scripts. The build checks each extracted tree (every file and symbolic link, the native binaries included) against a committed digest before Claude Code's own postinstall runs, and again after it.
- On locally built images, the [network probe](../images/trust/tls_probe.py) recorded curl, Python's `ssl`, httpx, requests, botocore, the installed pips and a new virtual environment's, git, Node, gh, Claude Code and Litestream refusing both forged chains with certificate errors, and verifying GitHub, Anthropic, OpenAI and R2 endpoints. Codex prints no cause, so its refusal is inferred, not shown: it connected and got no answer, twice, and with the forged roots added to its own OpenSSL's trust (`SSL_CERT_DIR`) it got the forged server's answer. Against a local server, the same signature came with OpenSSL's "unknown ca" alert from Codex. Deployed images have not been probed.
- Codex 0.164.0 adds two fields to `~/.codex/auth.json` (`tokens.login_owner_id`, `tokens.oauth_provenance`). Its path, mode, in-place write, status output and logout are unchanged, and the platform copies the file as opaque bytes. In local offline checks with synthetic logins, 0.163.0 and 0.164.0 each read, refresh and sign out with the other's file, and a file restored on a second computer stays signed in. Claude Code 2.1.311's login file and sign-in commands are unchanged.
- Signing in from the setup page reads the CLIs' own login output. It is tested against transcripts of Claude Code 2.1.311 and Codex 0.164.0 (Claude's link on `claude.com/cai/oauth/authorize`, Codex's on `auth.openai.com/codex/device` with a four-and-five-character code). A CLI whose output changes fails an attempt as "unexpected", and the page offers the terminal, so a version bump must recapture them. A computer whose supervisor's `hello` names no `sign_in` feature (an image before it) gets the terminal instead of the buttons.

**Runtime and CLI behaviour seen on staging (27 October 2026).** A staging run of the computer image found the following; the fixes are in source and qualified locally (Docker and the Workers runtime), not yet on Cloudflare:

- **Claude Code 2.1.311's fullscreen upsell.** While no settings layer names a renderer (`tui`), Claude Code asks "Try the new fullscreen renderer?" on its first three starts. Omnigent's harness can't answer it, so the first session failed. The computer image now installs `/etc/claude-code/managed-settings.json` (root's, mode 0644) with `{"tui": "default"}`. These managed settings take precedence over the person's and Omnigent's own settings files, so the computer always uses the default renderer. No other startup dialog of 2.1.311 blocks a start the harness drives:
  - Omnigent itself records onboarding as done and the workspace as trusted, and pre-approves project MCP servers.
  - An unanswered Consumer Terms update on the account could still show its dialog.
- **Claude Code 2.1.311 defaults to Auto mode** when no permission mode is set, and Omnigent's harness sets none. Omnigent's policy hooks still run on every tool call. Claude now asks for permission, and so raises Omnigent's approval prompt, only for what Auto mode doesn't decide itself.
- **`durable_object` containers.** The hostname, the Durable Object's 64-character ID, is not in `/etc/hosts`, so `sudo` warned on every call. `/` was owned by uid 2346, not root (the image's own layers give it to root), so Claude Code refused every directory for its cross-session messaging sockets and turned that messaging off. Claude Code checks every directory up to `/`, so `CLAUDE_CODE_TMPDIR` and `XDG_RUNTIME_DIR` don't help. The supervisor, as root at start, maps the hostname to 127.0.1.1 and gives `/` back to root. Both changes are idempotent and best-effort.
- **Runner environment.** Omnigent's host passes a runner only an allowlist of its environment. That allowlist left out the image's Claude Code settings (telemetry, error reporting and updates off). The supervisor now names those settings in the host's `OMNIGENT_RUNNER_ENV_PASSTHROUGH`.
- **Sandbox SDK 1.0.0 retries nothing.** Its shim uploads each part once, and when R2 fails a part, its gateway answers 502 with R2's message. One lost connection ("Network connection lost.") therefore failed a whole save. WorkspaceDO now repeats the whole upload after a transient failure: a 502, 503 or 504 from the gateway, or a lost or reset connection. It tries twice more, after 5 s and then 15 s, within the same upload deadline. A failed attempt leaves no object, and only the attempt that returns a record is published.

These are source-inclusion statements. They do not establish runtime behavior on an uninspected image. The main server registers the [Cloudflare launcher](../images/server/cfo_server/launcher.py) (launcher protocol version 1) and [disables GitHub linking](../images/server/cfo_server/app.py). The platform Worker's [internal platform bridge](../worker/src/internal/platform-api.ts) verifies signed launcher calls and reaches ControlDO and WorkspaceDO, which is wired in source to its container, intercepts and fenced backup gateway. That chain is tested in the Workers runtime with a simulated container; it has not run on Cloudflare with the computer image. Fork capabilities do not make those product integrations complete.

The [wire contracts](../contracts/README.md) define launcher/supervisor protocol version 1, workspace/control interface version 1, workspace/credential format version 1 and checkpoint-policy version 1. Receivers must check the versions they support before effects. Exported JSON Schema covers shape constraints; cross-field refinements and policy/signing/tree calculations also need tests against each actual receiver. The [generic Python fixture tests](../python/tests/test_contracts.py) cover valid/invalid schema fixtures, and the [vector tests](../python/tests/test_contract_vectors.py) use independent reference calculations. They do not prove that an unfinished supervisor applies all refinements. The WorkspaceDO controller refuses unsupported launcher, supervisor, intercept-props and interface versions before any effect. Every command shape it sends is recorded in a [corpus](../worker/test/fixtures/workspace-commands.json) that the supervisor's [actual parser](../images/computer/cfo_computer/contract.py) accepts in the [Python tests](../python/tests/computer/test_workspace_commands.py). That shows the two parsers agree; it is not a test of an assembled supervisor. ControlDO refuses a newer control interface version before parsing, parses every call with the contract, accepts every valid control fixture and refuses every invalid one before any effect, in the Workers runtime. A randomized test checks that the contract's fake ControlDO, which WorkspaceDO's own tests use, answers the same calls the same way. In the Workers runtime the routes, the backup gateway and ControlDO's reconciliation also run against the real WorkspaceDO, which runs against the real ControlDO, with only the container and the clocks simulated; the simulated container speaks `sandbox-shim`'s backup protocol, so the Sandbox SDK's real `DirectoryBackup` and the real gateway move the bytes to local R2. A reservation grant carries `maxInstanceSize` (optional, for an older ControlDO during a deploy); a WorkspaceDO that cannot confirm the cap gives the slot back rather than start. None of this is a deployed run.

Current [CI](../.github/workflows/ci.yml) runs the workspace's Node checks, the root `python/` project, limited canary checks, explicit platform and [web](../worker/wrangler.web.jsonc) bundles, and builds/tests the existing server image targets. Its image suite excludes S3/fault integration and runs without external networking. The [scripts test configuration](../scripts/vitest.config.ts) already includes restore-drill staging tests in Node with fakes. Restore-drill Python and real-platform qualification remain separate; the added CI checks do not change the source pins or assembly status above.

The [canary scanner](../scripts/canary-scan.ts) detects synthetic markers and exact configured values in its supported paths/formats. A clean result is bounded evidence about those values; it is not general proof of no credentials, a whole-repository/history/image scan, or publication approval. Incomplete scans fail.

For every qualification run record platform and fork revisions, actual Worker build/deployment IDs, final server/computer manifest digests and architecture, CLI/SDK/Litestream versions, packaged contract/policy assets, test commands/results, known exclusions and remaining runtime obligations. Image IDs from local tests must be labelled separately from registry manifest digests. Do not use mutable “latest” tags as the record.
