# Secret and credential inventory

Record each new credential's purpose, audience, custody, persistence and revocation before using it. Values, login files, account identifiers and personal data do not belong in source, fixtures, test snapshots, build images, public evidence or logs. This inventory describes the server base and accepted future computer/connection design; [compatibility](compatibility.md) identifies what is actually included.

## Handling rules

- Keep deployment credentials on the authorized installer's computer. CI uses ordinary pull requests, a read-only repository token and no persisted checkout credentials; untrusted builds receive no provider/deployment secrets.
- Pass secrets through the checked bootstrap/staging tooling's prompt or stdin, not command arguments, tracked configuration or shell history. The bootstrap generates the owner's initial password itself when none is given and puts it on the clipboard through the clipboard tool's standard input; it is never printed, logged, put in arguments or the environment, or written to a named file, and the person stores it in their password manager before the run uploads it. It reaches Wrangler as every other uploaded secret does (below). The tooling uses transient restricted files/open descriptors for deployment. Preserve its target/account checks; do not replace it with an unchecked bulk secret command.
- The bootstrap makes the installation's R2 token itself, from the installer's `cf` login, so that no one copies storage keys out of the dashboard. The token's value arrives on `cf`'s captured output and is never printed, logged, written or put in arguments or the environment. Its derived key pair reaches Wrangler like every other Worker secret the tooling uploads: through a descriptor of an already unlinked file in a memory-backed directory: the user's runtime directory (a private tmpfs on most Linux systems), else Linux's `/dev/shm`, each used only when its filesystem is checked to be tmpfs or ramfs. Only where neither is, as on macOS, does it fall back to the system's temporary directory, which may be on disk for as long as the upload reads it.
- Treat platform secret changes as releases. Removing bootstrap credentials requires durable initialization, not only a successful local account query. Key rotation requires overlap and post-release checks.
- A release that changes the server's configuration or image takes effect through one controlled server restart. A container receives its environment and image only when it starts, and the new platform version adopts the running container, so until the restart the server keeps its previous values. The watchdog compares the fingerprint of the container's environment, image and size (a one-way digest, stored by the server's Durable Object and never logged) with the one the running container started with, and replaces an answering server once: SIGTERM, the entrypoint's final sync (with the stop grace the container's own settings gave it, even if the release lowers it), then a start that restores the database. Expect a short outage per such release, recorded with the cause `config_changed`; a start still restoring or initializing is replaced only once it answers, and recovery mode is never restarted. The bootstrap counts its release complete only when the restarted server, running the released configuration, reports a durable owner.
- Copy declared native login files as opaque bytes. Do not parse or log them. Use synthetic runtime-generated canaries in tests, and record which paths, formats and values a scan covered.
- Signing in from the setup page relays only what the terminal relayed: the one-time code the person pastes for Claude, from the page through WorkspaceDO to the unmodified CLI's own login on the computer; nothing for Codex. The provider's link, Codex's device code and the pasted code are never logged or stored: not in Workers Logs, Durable Object storage (an operation's journal included), the computer's files, the supervisor's logs or alerts, or a save. The supervisor keeps them in memory for the attempt's life only. Tests plant synthetic canaries in all of them and scan each of those places.
- Do not log credential-bearing request headers or terminal/viewer streams. Both production Worker configurations set `observability.logs.invocation_logs: false` while retaining structured console logs. The server container's own output also goes to Workers Logs (set on its container entry, because a `durable_object` container does not inherit the Worker's setting); the image keeps credential values out of it, and its integration suite scans it for the run's generated secrets. A computer container's output is not logged. Do not send credential-bearing traffic through a Worker with invocation logs enabled; custom headers such as `X-Omnigent-Host-Token`, `X-Omnigent-Runner-Tunnel-Token` and `x-api-key` may be recorded. Verify the deployed configuration and keep credentials out of console logs.

## Installer-local material

| Material | Custody / removal |
| --- | --- |
| Wrangler and `cf` authentication | Existing CLI-managed stores on the installer computer; separate logins. Use the relevant CLI logout/revocation workflow when withdrawing access, rather than printing credentials. |
| GitHub CLI authentication | Existing CLI-managed credential store or keyring; do not assume a token file exists. Git/SSH credentials are separate from platform deployment credentials. |
| Staging configuration, registry and locks | `CFO_STAGING_DIR` or the staging tool's default config directory, outside the repository. Contains identifying account/zone/ownership data. Tooling manages registry/lifecycle records; do not delete locks to bypass another run. |
| Bootstrap journal | `CFO_INSTALL_DIR` or the installation tool's default config directory; restricted mode-0600 file in a mode-0700 directory. Identifying installation plan/progress and the R2 token's name and ID (the S3 access key ID, not its secret), not passwords or keys. Keep until the installation is intentionally retired: removing the R2 token reads the ID from it. |
| Optional staging Tunnel/service-token credentials | Only reviewed staging manifests use these; normal computer transport does not depend on an Access service token. Secrets travel through guarded input/upload paths, are scoped to their staging resources and are removed by the guarded teardown. Expiry alone is not proof of resource deletion. |
| Real native CLI test logins | Only the reviewed computer under test and its intended credential checkpoint; sign out after the run and verify restored absence. Provider-side revocation is separate from local logout. |

## Implemented server-base settings

Only `SERVER_ENV_<NAME>` values deliberately forwarded by the [server environment adapter](../worker/src/server/server-env.ts) become `<NAME>` in the container. This is an explicit prefix mapping, not a claim that containers contain no secrets. The image also pins or removes settings it does not support.

| Worker-held name | Purpose and container use | Removal / rotation |
| --- | --- | --- |
| `SERVER_ENV_OMNIGENT_ACCOUNTS_INIT_ADMIN_PASSWORD` | Initial owner bootstrap; explicit username is a non-secret setting. Forwarded only to the server while needed. Generated by the bootstrap (24 characters, about 140 bits) and handed to the person on the clipboard, unless they type one or supply it on stdin. | Checked bootstrap release removes it only after current-installation initialization and replication proof. The running server loses it at the restart that applies the release; the bootstrap waits for that restart. The owner then verifies sign-in and changes the password as appropriate. |
| `SERVER_ENV_CFO_INSTALLATION_INITIALIZED` | Non-secret expectation deliberately stored as a secret so ordinary configuration deploys cannot erase it. A missing/old replica must produce recovery mode. | Do not clear it to force setup. Recovery requires an explicit plan. |
| `SERVER_ENV_OMNIGENT_ACCOUNTS_COOKIE_SECRET` | Server session cookies. | Deliberate secret release. Existing cookie sessions end at the server restart that applies it: from then on the old key's cookies are refused and everyone signs in again. Until that restart the old key stays in use. This is not by itself complete revocation of every bearer/grant. |
| `SERVER_ENV_LITESTREAM_ACCESS_KEY_ID`, `SERVER_ENV_LITESTREAM_SECRET_ACCESS_KEY` | Bucket-scoped database replication credentials. The image gives these to Litestream and removes them from the app child's environment. Litestream's restore and replicate processes receive only these and basic process settings (an allowlist): never the bootstrap password, cookie secret, launcher key or artifact-storage credentials. The allowlist limits what each process is given; it is not isolation inside the container, where every process runs as root and, under the `durable_object` policy, has root's capabilities whatever its user. | Rotate/revoke the scoped R2 credential; the new one is used from the server restart that applies the release. Do not broaden it to computer-checkpoint buckets. |
| `SERVER_ENV_AWS_ACCESS_KEY_ID`, `SERVER_ENV_AWS_SECRET_ACCESS_KEY` | Bucket-scoped credentials for Omnigent's artifact store: uploaded files, session resources and agent bundles, kept in an R2 bucket of their own. Omnigent's S3 store reads them (as `boto3` does). The image gives them to the app child only; Litestream's allowlist excludes them. The bootstrap's one R2 token covers the replica's and the artifacts' buckets: its key pair is set under both pairs of names, so each process still receives only its own pair. | Rotate/revoke with the replica's pair: when one token covers both buckets, change both pairs in the same release (one controlled restart). Do not broaden the token to computer-checkpoint or browser-profile buckets. |
| The installation's R2 token (a Cloudflare user API token, not a Worker secret) | The source of both R2 key pairs: "Workers R2 Storage Bucket Item Write" (read, write and list objects) on exactly the replica's and the artifacts' buckets, named `<platform Worker>-r2--<installation ID>--<UTC time of its create>`, made by `bootstrap.ts run` with the installer's `cf` login. The access key ID is the token's ID and the secret key the SHA-256 of its value; Cloudflare shows the value only when it creates the token. No expiry for an installation; a staging installation's expires a day after its deployments. It belongs to the user who made it and stops working if that user leaves the account. A login that may not make tokens gets the dashboard step, and the installer supplies a hand-made token's values. | `cf`'s own sign-in may create tokens but not list, roll or delete them (403). A re-run never rolls: it reuses the pair the Worker holds, and makes a new token only when the Worker has none, recording the old one (its value gone) to delete. `bootstrap.ts remove-r2-token` deletes the tokens where Cloudflare allows it (refused while a Worker with the platform Worker's name exists, unless `--yes`); otherwise it names each, with the one link and click that delete it, keeps them recorded and exits 1. The staging tool's teardown and `sweep --yes` do the same for a staging installation's. Deleting the token in use stops replication and the server's start at once. |
| `SERVER_ENV_OMNIGENT_ARTIFACT_URI`, `SERVER_ENV_AWS_ENDPOINT_URL_S3`, `SERVER_ENV_AWS_REGION` | Non-secret variables: the artifact bucket (`s3://<bucket>[/<prefix>]`, never the replica's bucket), its S3 endpoint (`https://<account>.r2.cloudflarestorage.com` for R2) and region (`auto`). The image refuses to start without the URI and its credentials (exit 78), initialized or not: on the container's disk, uploaded files would be lost at every replacement and at every release's controlled restart. `CFO_ALLOW_LOCAL_ARTIFACTS=true` permits the disk for tests and local runs only. Omnigent reads the bucket as it starts, so a bucket the credentials cannot reach stops the start. The image sets `AWS_REQUEST_CHECKSUM_CALCULATION` and `AWS_RESPONSE_CHECKSUM_VALIDATION` to `when_required` unless the deployment names other values. | Changing the bucket is a deliberate release; copy existing objects first (see [recovery](operations/recovery.md#uploaded-files)). |
| `SERVER_ENV_CFO_LAUNCHER_SIGNING_KEY`, `SERVER_ENV_CFO_LAUNCHER_SIGNING_KEY_ID` | The launcher API's HMAC key (its UTF-8 bytes, at least 32) and its key ID; separate from the credential key service's key. The server's Cloudflare launcher signs with it as `CFO_LAUNCHER_SIGNING_KEY`, and the platform Worker's `platform.internal` receiver verifies with the same Worker secrets. Only the server container receives the signing pair. With neither set, the launcher stays registered but refuses every call, and so does the receiver; one alone or a malformed value stops the app. Not yet set by any deployment tool. | Rotate as a deliberate platform release with overlap: move the old key and ID to `CFO_LAUNCHER_SIGNING_KEY_PREVIOUS` and `CFO_LAUNCHER_SIGNING_KEY_PREVIOUS_ID` (Worker-only), set the new current pair; the watchdog's controlled restart that applies this release makes the server sign with the new key. Delete the previous pair only after that restart. |
| `SERVER_ENV_OMNIGENT_GITHUB_APP_CLIENT_ID`, `SERVER_ENV_OMNIGENT_GITHUB_APP_CLIENT_SECRET`, `SERVER_ENV_OMNIGENT_GITHUB_APP_REDIRECT_URI`, `SERVER_ENV_OMNIGENT_GITHUB_APP_ID`, `SERVER_ENV_OMNIGENT_GITHUB_APP_SLUG` | The installation's own GitHub App, for Omnigent's GitHub linking (D22): its client secret is a secret; the client ID, numeric ID, slug and callback (`https://<hostname>/v1/connections/github/callback`) are not, but are kept as secrets so that ordinary deploys cannot erase them. Set by `bootstrap.ts github-app` from GitHub's answer to the App's manifest, through the same descriptor transport as every other secret; never shown, logged, written or put in an argument. The server receives exactly these five, and only when the key service's signing pair is also set; Omnigent uses the client secret for the OAuth code exchange and token refresh. The App's private key and webhook secret, which GitHub's answer also carries, are discarded: Omnigent's linking uses neither, and the image removes `OMNIGENT_GITHUB_APP_PRIVATE_KEY` if one is ever set. | Rotate the client secret on GitHub's App settings page and set the new value as a release; the old one stops at GitHub when deleted there. `bootstrap.ts github-app --replace` registers a new App (the owner then deletes the old one on GitHub and links again). Removing the five secrets turns linking off at the next restart; the stored records stay unreadable to anyone without the key service. |
| `SERVER_ENV_OMNIGENT_CREDENTIAL_HTTP_SIGNING_KEY`, `SERVER_ENV_OMNIGENT_CREDENTIAL_HTTP_SIGNING_KEY_ID` | The HMAC key (its UTF-8 bytes, at least 32; the installer generates 32 random bytes as hex) and key ID with which the server's credential store signs its calls to the key service on `platform.internal`; separate from the launcher's key. The server and the Worker's key service read the same secret. Generated by `bootstrap.ts github-app` when the Worker holds none; never replaced by it. | Rotate as a release with overlap: move the old pair to `CFO_KEY_SERVICE_SIGNING_KEY_PREVIOUS` and `CFO_KEY_SERVICE_SIGNING_KEY_PREVIOUS_ID` (Worker-only), set the new pair; delete the previous pair after the controlled restart. |
| `CFO_KEY_SERVICE_RECORD_KEYS` | The key service's record keys: JSON `{"keyId", "current", "versions": {"<n>": "<32 bytes, base64url>"}}`, a Worker-only secret (no `SERVER_ENV_` prefix), so no container receives it. Each record of Omnigent's credential store is sealed with AES-256-GCM under a key derived from the current version and the record's identity; the record names its key ID and version. Generated once by `bootstrap.ts github-app` (key ID `<installation ID>.records`, version 1) and never replaced by it. Losing it makes every stored GitHub link unreadable (the owner links again); it is not in the database or its replica. | Add a version and make it current as a release; keep every older version while records use it (Omnigent re-seals a record under the current version when it next writes it, on a refresh or reconnect). Never reuse a version number for other key material. A malformed value makes the key service refuse every call. |
| Access issuer/audience, hostname and owner pin | Ingress configuration. The salted pin permits guessing attacks against candidate addresses and is not a confidential identity store. | Update through installation configuration; keep identifying configuration out of public run records. |

There is no platform Omnigent login. Omnigent's GitHub linking is the one credential provider the server enables (see [GitHub linking](architecture.md#github-linking)); Databricks, AWS KMS and Vault settings are removed from the app's environment. Setting other integration environment variables does not enable unfinished wiring.

## Accepted computer/connection credential design

| Class | Intended custody and persistence |
| --- | --- |
| Host launch token | Supervisor/host memory and process environments, stable only for that live incarnation; no disk login or checkpoint copy. Generation/start claims and launch-token-only registration protect host identity. |
| Runner binding/delegated tokens | Runtime authority and excluded harness-secret families; short-lived delegated owner-equivalent access with explicit approval/account/policy restrictions. Broad access to other computers' work remains possible. |
| Native Claude/Codex logins | Declared credential checkpoint files: `.claude/.credentials.json`, `.claude/.device-keys.json`, `.codex/auth.json`, `.codex/.credentials.json`, relative to the computer home. No Omnigent login/refresh-grant file is declared. |
| Native-harness continuation | Save configuration, rollouts, transcripts, private Codex home and undelivered-event state. Exclude classified credential families and temporary siblings, not whole continuation directories. |
| Codex key-provider API key | Mode-0600 `provider_key` in `.omnigent/codex-native/<bridge>/`, read through a reference in generated config and removed on app-server close. `provider_key.*` temporary files are also excluded. Saved configuration uses references; computer key-provider configuration must not inline the key. |
| Native GitHub linking | In source (above): the server's GitHub App settings and encrypted access/refresh records. The Worker holds the encryption keys; the server uses plaintext for refresh and vending. The host broker supplies only the access token to git/gh at runtime, without helper-argv/gh token files. The refresh token stays on the server. Other native providers remain unconfigured. Not yet run on Cloudflare. |
| Worker key service | In source (above): versioned record keys in a Worker-only secret plus the server's separate signing pair. Record context, key ID and version are authenticated; old key versions remain readable while records use them. |
| Launcher and gateway signing | Separate server-side bridge credentials with key IDs and overlap for rotation. They authorize private operations, not public access. Keep launcher and key-service signing authority separate. The launcher's and the key service's signers and receivers are in source (above); the gateway's credentials remain planned. |
| Platform connected-account tokens and wrapping keys | Planned Worker-side connection service; raw connected-account credentials do not reach computers. This differs from the deliberate native GitHub exception. |

The [policy authority](../contracts/src/checkpoint-policy.ts) classifies secret families; the [manifest contract](../contracts/src/manifests.ts) declares opaque login files/tombstones. Workspace restore filters every layer; the newest credential generation/order is installed separately. A sign-out needs a published tombstone and restore verification so older saves cannot reintroduce login files.

The accepted design keeps checkpoint buckets private and accessible through Worker bindings, with no S3 API token for computers. Version one relies on R2 encryption at rest, without application-level checkpoint encryption. Someone controlling the Worker/account can read saved logins. The database replica holds Omnigent's credential-store records (the GitHub link) only as ciphertext sealed by the Worker's key service; encryption-key separation does not remove server plaintext access.

## Verification and incident response

The [canary scanner](../scripts/canary-scan.ts) checks synthetic markers and exact configured values in selected supported inputs. Its existing CI invocation is not a whole-repository/history/image or arbitrary-secret scan; incomplete input fails. Actual checkpoint qualification additionally walks/decompresses every published layer, covers all live token generations and encoded forms, and proves detection with planted values. Those product tests are still pending integration. The computer's opt-in check before each save (`/var/cfo/rc53/enabled`, for staging) scans each staged layer for the live credentials it collects in memory. It collects credentials only:
- values whose field, header, variable or file name says they are one;
- bearer tokens;
- values in a credential format;
- a credential helper's inline key;
- the broker's GitHub token.

It never collects identifiers such as session IDs, tool names, server URLs or account IDs, which Omnigent and the CLIs write into files that are meant to be saved. The [collector](../images/computer/cfo_computer/rc53_collect.py) documents the rule and the file formats it was checked against.

Use [security operations](operations/security.md) for provider-side revocation, account-generation invalidation, persistence review and safe evidence collection. A computer wipe or local CLI logout alone does not establish revocation of copied credentials.
